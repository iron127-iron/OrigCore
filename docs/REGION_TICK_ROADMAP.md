# 區域化 Tick 藍圖（R001–R006）

> ## 現況
>
> **區域化 Tick 在 OrigCore 0.1.0 尚未實作。**
>
> `config/origcore.yml` 中的 `threading.region-tick.enabled` 是**保留設定**，
> 一律強制為 `false`。把它設成 `true` 只會得到一則警告，不會有任何效果。
>
> 本文件是**後續規劃**，不是已完成功能的說明。

所有相關工作都在 `exp/region-tick` 分支上進行，**未經驗證不得合併回 `main`**。

---

## 1. 為什麼 0.1.0 不做

區域化 Tick 需要把 Minecraft 的世界狀態切成可獨立處理的區域，並保證：

- 跨區域的互動（實體碰撞、紅石、液體流動、方塊更新、傳送門、村莊、AI 目標選擇……）仍然是正確的。
- 插件看到的事件順序與執行緒語意仍然可接受。
- 任何一個區域的延遲不會以不可預期的方式影響其他區域。

任何一項做錯，代價都是**世界損毀或難以追蹤的資料競爭**。因此 0.1.0 先在穩定的 `main` 上把：

1. 受控的工作池與有界拒絕策略，
2. 執行緒邊界與違規偵測，
3. 可觀察的診斷指標，

做對、做誠實，再來處理區域化。

**先有正確的邊界與可量測的基礎，才有資格談平行化。**

---

## 2. Folia 的角色：參考，不是移植

Folia 是 PaperMC 的區域化實作，是重要的架構參考：

- 可以研究它如何定義區域（region）、如何分割世界、如何處理跨區域工作。
- 可以參考它的 API 設計與失敗案例。

但 OrigCore **不會**整套移植 Folia：

- 不複製 Folia 的程式碼。
- 不在沒有自己驗證的情況下採用其架構決策。
- 不因為「Folia 這樣做」就跳過驗證。

同時，OrigCore 不會聲稱與 Folia 相容（見 `docs/COMPATIBILITY.md`）。

---

## 3. 分期計畫

每一期都有**明確的驗收標準**。無法通過驗收標準就不進入下一期。

### R001 — 前置研究與邊界定義

| 項目 | 內容 |
| --- | --- |
| 目標 | 盤點 Minecraft 世界狀態，界定「區域本地」與「全域共享」的資料，並定義不變條件。 |
| 前置條件 | `main` 上的 0.1.0 已穩定。 |
| 工作項目 | 1. 找出所有在 Tick 中被讀寫的世界狀態。<br>2. 標記哪些狀態可分割（區塊本地）、哪些不可（全域計數器、跨區塊結構）。<br>3. 定義「區域」的邊界與其生命週期。<br>4. 列出所有跨區域互動路徑。<br>5. 產出「不變條件清單」與「已知不可分割清單」。 |
| 驗收標準 | 文件的盤點結果可被他人重複驗證；每一項「可分割」的判斷都有呼叫路徑依據。 |
| 產出 | `docs/REGION_TICK_RESEARCH.md`（僅在實驗分支）。 |
| 風險 | 盤點不完整 → 後續全部不可靠。 |
| **不進入下一期的條件** | 有任何一項世界狀態無法被分類。 |

### R002 — 區域化排程骨架（不動主執行緒路徑）

| 項目 | 內容 |
| --- | --- |
| 目標 | 建立區域資料結構與排程骨架，但**完全不改變**目前的 Tick 行為。 |
| 前置條件 | R001 完成。 |
| 工作項目 | 1. 定義區域識別與區域 → 執行緒的對應（僅資料結構）。<br>2. 建立「區域工作」提交介面，重用既有的 `WorkerPool` 精神（固定大小、有界、拒絕）。<br>3. 加入開關，預設 **關閉**；關閉時路徑必須與 0.1.0 完全相同。 |
| 驗收標準 | 開啟與關閉開關時，行為與 0.1.0 完全一致（以 `origcoreTest` + 煙霧測試驗證）。 |
| 風險 | 在骨架階段不小心改變了行為。 |
| **不進入下一期的條件** | 關閉開關時無法證明行為與 0.1.0 相同。 |

### R003 — 讀寫集合分析與不變條件

| 項目 | 內容 |
| --- | --- |
| 目標 | 針對每個候選工作，明確列出它的讀集合與寫集合，以及與其他工作共享的狀態。 |
| 前置條件 | R002 完成。 |
| 工作項目 | 1. 每個候選工作都要有讀集合／寫集合。<br>2. 用 `ThreadSafetyGuard` 的 `STRICT` 模式驗證「沒有意外的共享寫入」。<br>3. 為每一項跨區域互動定義處理策略（延後、鎖定、或明確禁止平行）。 |
| 驗收標準 | 每個候選工作的讀寫集合都有依據；`STRICT` 模式下不會出現未預期的違規。 |
| 風險 | 讀寫集合漏掉隱含共享（例如靜態快取、單例）。 |

### R004 — 單區域平行 Tick 原型（預設關閉）

| 項目 | 內容 |
| --- | --- |
| 目標 | 在**受控且可關閉**的前提下，讓單一區域能在背景執行緒上進行 Tick。 |
| 前置條件 | R003 完成。 |
| 工作項目 | 1. 實作最小範圍的區域 Tick（先限制在可證明安全的少量工作）。<br>2. 跨區域狀態一律回到主執行緒處理。<br>3. 提供即時開關，可在不重啟的情況下關閉（用於緊急回退）。<br>4. 預設值必須是**關閉**。 |
| 驗收標準 | 1. 預設關閉時行為與 0.1.0 相同。<br>2. 開啟時，指定的正確性測試（見 R005）全部通過。<br>3. 世界存檔後重新載入的結果一致。 |
| 風險 | 最危險的一期。任何資料競爭都可能造成世界損毀。 |

### R005 — 正確性驗證框架

| 項目 | 內容 |
| --- | --- |
| 目標 | 建立可重現的驗證，證明區域化 Tick 不會改變世界的最終狀態。 |
| 前置條件 | R004 開始後即可並行進行。 |
| 工作項目 | 1. 可重現的壓力情境（固定種子、固定操作序列）。<br>2. **確定性（determinism）測試**：同一序列在開啟／關閉區域化 Tick 時，最終世界狀態必須相同。<br>3. 跨區域互動的專項測試。<br>4. 長時間執行的穩定性測試與執行緒傾印分析。 |
| 驗收標準 | 開啟與關閉時的最終狀態在定義的容許範圍內一致（並明確記錄哪些狀態被容許不同、為什麼）。 |
| 風險 | 測試覆蓋不足 → 產生「通過測試但實際損毀世界」的假安全感。 |

### R006 — 效能與決策

| 項目 | 內容 |
| --- | --- |
| 目標 | 用量測資料決定是否值得合併，以及是否需要 Folia 式的區域化 API。 |
| 前置條件 | R005 通過。 |
| 工作項目 | 1. 依 `docs/BENCHMARKS.md` 的方法做對照量測（與 `main` 的 0.1.0 比較）。<br>2. 記錄 MSPT 百分位數、TPS、可承載玩家數。<br>3. 明確列出**未改善**與**變差**的情境。 |
| 驗收標準 | 1. 有可重現的資料，且環境充分記錄。<br>2. 若資料不足以支持合併，結論就是**不合併**。 |
| 風險 | 為了「有成果」而選擇性引用資料。**這是不被允許的。** |

### 合併規則

- 只有在 R006 明確判定「值得合併」時才合併。
- 合併時必須同時合併 R005 的驗證框架。
- 合併後 `region-tick.enabled` 的預設值仍然是 `false`，直到有足夠的實際運行資料支持改變它。

---

## 4. 禁止事項

在整個 R001–R006 期間，以下事項一律禁止：

1. 在 `main` 上直接進行區域化 Tick 的實驗。
2. 把未經驗證的區域化程式碼合併回 `main`。
3. 以「核心越多就越快」作為設計依據或宣傳說法。
4. 用 `ConcurrentHashMap` 之類的容器掩蓋本質上不安全的共享存取。
5. 刪除或重排上游檔案，讓後續上游升級變得不可行。
6. 對外聲稱已支援區域化 Tick，直到 R006 完成且合併。
7. 移除 `region-tick.enabled` 預設為 `false` 的保護，除非有明確的驗證與文件更新。

## 5. 分支與開關策略

| 項目 | 規則 |
| --- | --- |
| 開發分支 | `exp/region-tick` |
| 合併來源 | 只能從 `main` 拉取更新，**不得**反向合併未驗證內容 |
| 設定開關 | `threading.region-tick.enabled`，預設 `false` |
| 緊急回退 | 必須能在不重新產生世界的情況下關閉 |
| 標示 | 實驗期間的所有產出都必須標示「實驗性、可能損毀世界」 |
